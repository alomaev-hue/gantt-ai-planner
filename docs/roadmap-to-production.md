# Roadmap to production

Этот документ описывает: что в текущей реализации — осознанный технический долг (принят ради срока в 2–3 дня), чего не хватает для реального продакшена, какие риски у решения в целом и в каком порядке имеет смысл закрывать долг. Ссылки на код и раздел «Ограничения» — в `README.md`; полная спецификация — в `docs/superpowers/specs/2026-09-25-gantt-ai-planner-design.md`.

## Осознанный технический долг

Ограничения, принятые сознательно ради сроков — не баги, а выбор объёма:

| Ограничение | Почему принято сейчас |
|---|---|
| Один uvicorn-воркер, шина событий (SSE) и блокировка сессии — в памяти процесса | Демо на один-два одновременных пользователя не требует горизонтального масштабирования; `LISTEN/NOTIFY` через Postgres — прямой путь вперёд, но лишняя сложность для MVP |
| Только рабочие дни, без праздничного календаря | Праздники варьируются по стране/региону и требуют отдельного источника данных; для демо-плана не критично |
| Только зависимости «конец → начало» (FS), без SS/FF/SF и отрицательного лага | В большинстве реальных Ганта-планов FS покрывает основной поток; остальные типы связей — это отдельная ветка в планировщике (CPM) и в UI рисования связей |
| Нет вех (задач нулевой длительности) | В модели `duration: int (1..999)` веха — вырожденный случай, требующий отдельной обработки в раскладке и в Excel-формате |
| Один исполнитель на задачу, без мультиисполнителей | Расчёт «перегрузки» и модалка задачи рассчитаны на одного `assignee`; мультиисполнители умножают эту логику |
| План хранится целиком как JSONB-снимок, без отдельных таблиц задач | При лимите 500 задач на план это проще и быстрее в разработке, чем нормализованная схема; отмена/повтор — просто переключение указателя на версию |
| Сессии по cookie без аутентификации, план не расшаривается между пользователями | Соответствует формату «публичное демо»; полноценные учётные записи и совместные планы — это отдельная модель данных (владение, права доступа) |
| Нет офсайт-бэкапов (только план на локальный `pg_dump` на VPS, см. спецификацию §13) | Бэкап-скрипт (`deploy/backup.sh`) и его расписание — часть деплоя, который на момент написания этого документа ещё не выполнен на VPS |

## Чего не хватает для продакшена

### Надёжность и масштабирование

- **`LISTEN/NOTIFY` в Postgres + несколько воркеров uvicorn.** Сейчас шина событий (`backend/app/services/events.py`) и блокировка сессии на время хода агента (`backend/app/services/locks.py`) — это `asyncio`-примитивы внутри одного процесса. Чтобы поднять больше одного воркера или несколько инстансов за балансировщиком, события нужно публиковать через Postgres (`LISTEN/NOTIFY` или отдельную очередь), а блокировку — через advisory lock в БД или Redis.
- **Нагрузочные тесты.** Нет ни одного профиля нагрузки (сколько сессий/сообщений в чат в секунду держит текущая конфигурация лимитов и `mem_limit` контейнеров). Нужно определить целевую нагрузку и прогнать хотя бы базовый сценарий (k6/locust) перед реальным трафиком.

### Модель предметной области

- **Праздники и рабочие календари** — расширение `backend/app/domain/calendar.py` источником праздничных дат (вручную/по региону).
- **SS/FF/SF-зависимости и отрицательный лаг** — расширение планировщика CPM (`backend/app/domain/scheduler.py`) и операций (`backend/app/domain/operations.py`), плюс UI для выбора типа связи при рисовании.
- **Вехи** — нулевая длительность как отдельный тип задачи в модели, расчётах и в Excel-формате.
- **Мультиисполнители** — смена модели `Task.assignee: str | null` на список, пересчёт логики перегрузки и модалки задачи.
- **Нормализация задач в БД при росте.** Пока план — один JSONB-снимок на версию (лимит 500 задач). Если лимит вырастет на порядок или понадобятся выборочные запросы/индексы по полям задач, план нужно нормализовать в отдельные таблицы `tasks`/`dependencies` с миграцией существующих версий.

### Многопользовательский режим

- **Аутентификация и общие планы.** Сейчас идентификация — это непрозрачный cookie-токен без пароля/логина; нет модели владения планом и прав доступа (просмотр/редактирование для нескольких людей на одном плане). Нужны: учётные записи, приглашения в план, разграничение прав.

### MCP

- **OAuth 2.1 для внешнего MCP.** В спецификации внешний доступ (Фаза 2) описан через статический Bearer-токен (`mcp_<token>`), выпущенный вручную в UI, — это упрощение для одного пользователя на сессию. Для реального многопользовательского сценария и для соответствия актуальным ожиданиям MCP-клиентов нужен полноценный OAuth 2.1 (authorization code + PKCE), а не долгоживущий статический токен.
- Сам внешний HTTP-эндпоинт `/mcp` с выпуском/отзывом токена — на момент написания этого документа не реализован (см. `README.md`, раздел MCP); таблица `mcp_tokens` в схеме БД уже создана заранее.

### Наблюдаемость

- **Мониторинг, алерты, трейсинг вызовов LLM.** Сейчас логируется только `session_id` (префикс), маршрут, статус, время ответа и число токенов (см. спецификацию §13) — без метрик (Prometheus/аналог), без алертов на рост ошибок/задержек LLM, без трейсинга цепочки «сообщение → вызовы инструментов → ответ» для отладки конкретного хода агента.

### Эксплуатация LLM

- **E2E-тесты на живом LLM.** Playwright e2e (`frontend/e2e/main.spec.ts`, джоб `e2e` в CI) работают на `LLM_PROVIDER=fake` — детерминированно и без затрат, но не проверяют реальное поведение модели. Перед сдачей предусмотрен только ручной чек-лист из 5–7 команд на живом ключе (спецификация §15); автоматического регресса на живой модели нет.
- **Eval-набор промптов.** Нет набора эталонных диалогов с ожидаемыми вызовами инструментов/результатами для регрессионной проверки качества агента при смене модели, промпта или версии SDK.

### Хостинг и соответствие

- **Хостинг в РФ под 152-ФЗ.** Текущий план — VPS не в РФ, LLM — внешний API Anthropic; обработка и хранение персональных данных граждан РФ в таком контуре не проработана и не разрешена без изменения архитектуры (хостинг и, вероятно, локальная модель — в РФ). Сейчас это закрыто эксплуатационно: в демо используются только вымышленные данные (см. README, «Безопасность и данные»).
- **Офсайт-бэкапы (restic).** Спецификация фиксирует только локальный `pg_dump -Fc` на самом VPS с хранением 7 дней (§13); копия на внешнее хранилище (S3-совместимое, через restic) — задокументирована как следующий шаг, но не реализована.

### Безопасность

- **CSP без `unsafe-inline`.** Текущая политика Caddy (`deploy/caddy/Caddyfile`) допускает `style-src 'self' 'unsafe-inline'` — уступка Tailwind/inline-стилям сторонних компонентов (в частности SVAR). Для более строгой политики нужны либо nonce/hash для стилей, либо отказ от инлайн-стилей в зависимостях.
- **Rootless Docker.** Контейнер приложения уже запускается непривилегированным пользователем (uid 10001, `read_only`, `cap_drop: ALL`), но сам Docker-движок на VPS работает как обычно (root daemon). Полностью rootless-режим Docker на хосте — отдельная работа по настройке сервера, не сделанная в рамках `deploy/bootstrap.sh`.

## Риски

| Риск | Пояснение | Что снижает риск сейчас |
|---|---|---|
| Недетерминированность LLM | Модель может по-разному интерпретировать одну и ту же команду, особенно при массовых правках | Атомарные пакеты операций с серверной валидацией, отмена целого хода агента, ручной чек-лист перед сдачей — но не полноценный eval-набор (см. выше) |
| Стоимость вызовов LLM | Публичное демо без аутентификации может привлечь нежелательную нагрузку на платный API | Лимиты на чат (30 сообщений/час на сессию, 500/сутки на всё приложение), `max_tokens` на ответ, отдельный workspace/ключ Anthropic с лимитом расходов |
| Зависимость от одного LLM-провайдера | Весь агент построен на Anthropic SDK и конкретном формате инструментов; смена провайдера — не тривиальная замена одной переменной | Слой `backend/app/agent/llm.py` абстрагирует вызов модели и позволяет добавить второй адаптер, но контракт инструментов и промпт написаны с оглядкой именно на Claude |
| Баги/ограничения SVAR Gantt | Сторонняя библиотека (в частности, для рассинхронизации шапки/таблицы или зависаний прокрутки, по опыту схожих проектов) | Версия зафиксирована (`2.7.3`), в спецификации записан запасной вариант — DHTMLX Community v10 (MIT); на сегодня перетаскивание/растягивание ещё не включено (Фаза 2), риск полностью не проверен |
| Единственный VPS (single point of failure) | Один сервер держит и БД, и приложение, и reverse proxy для этого и других сервисов пользователя; простой VPS = простой сервиса | Health-check и `restart: unless-stopped`, локальные бэкапы БД — но без резервного хоста и без офсайт-бэкапов (см. выше) отказ диска/провайдера теряет данные |

## Порядок закрытия

Приоритеты: **P0** — блокирует реальную эксплуатацию с настоящими пользователями/данными; **P1** — заметно повышает надёжность/качество, но сервис работоспособен без этого; **P2** — улучшения, которые можно откладывать надолго.

| # | Что | Приоритет | Почему в этом порядке |
|---|---|---|---|
| 1 | Завершить текущий план: внешний `/mcp` с токенами, drag/resize на диаграмме, деплой на VPS, демо-запись (Docker-образ и e2e на fake-LLM уже готовы) | **P0** | Без этого не закрыт даже заявленный в ТЗ объём — это не «долг сверху», а недоделанная база |
| 2 | Мониторинг, алерты и трейсинг вызовов LLM | **P0** | Без наблюдаемости невозможно вовремя заметить деградацию модели, рост ошибок или аномальный расход API — а именно это самый дорогой и самый непредсказуемый ресурс сервиса |
| 3 | Офсайт-бэкапы (restic) и проверка восстановления не «один раз вручную», а по расписанию | **P0** | Единственный VPS без внешней копии данных — это гарантированная потеря данных при первом серьёзном инциденте с диском/хостом |
| 4 | `LISTEN/NOTIFY` в Postgres + несколько воркеров uvicorn | **P1** | Нужно только при реальном росте одновременных пользователей; для текущего масштаба (демо/тестовое) риск невелик, но это первое, что упрётся в потолок при успехе продукта |
| 5 | Аутентификация и общие планы | **P1** | Меняет модель данных и права доступа — крупная работа, но без неё сервис остаётся демо для одного анонимного пользователя за раз, что ограничивает реальное применение |
| 6 | OAuth 2.1 для внешнего MCP | **P1** | Важно только после того, как заработает сам внешний `/mcp` (пункт 1); статический токен допустим как временное решение для одного пользователя |
| 7 | Нагрузочные тесты | **P1** | Нужны, чтобы осознанно выставлять лимиты и `mem_limit`, но без них сервис не небезопасен — просто конфигурация подобрана на глаз |
| 8 | E2e на живом LLM + eval-набор промптов | **P1** | Повышает уверенность в качестве агента при смене модели/промпта; отсутствие не блокирует работу сегодня, но усложняет безопасные будущие изменения |
| 9 | Праздники/календари, SS/FF/SF и отрицательный лаг, вехи, мультиисполнители | **P2** | Расширения модели предметной области, ценность зависит от реальных требований пользователей — делать по запросу, а не заранее |
| 10 | Нормализация задач в БД | **P2** | Оправдана только при заметном росте лимита задач на план или потребности в выборочных запросах — сейчас 500 задач в одном JSONB достаточно |
| 11 | Хостинг в РФ под 152-ФЗ | **P2** (переходит в P0, если появятся реальные ПДн) | Пока используются только вымышленные данные, это не блокер; становится обязательным условием ровно в момент, когда в план попадут настоящие персональные данные граждан РФ |
| 12 | CSP без `unsafe-inline`, rootless Docker | **P2** | Дополнительное усиление защиты сверх уже принятых мер (непривилегированный пользователь в контейнере, `cap_drop: ALL`, `read_only`); риск от их отсутствия ниже, чем у пунктов выше |
